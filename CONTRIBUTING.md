# Contributing to ChartGuard

ChartGuard is a portfolio project maintained by one person. Issues and pull requests are welcome; please read this first.

## Setup

- Node.js 22.12 or later (development targets Node 26, the active LTS; CI also runs 22 and 24), npm 11 or later (the lockfile is written by npm 11; `packageManager` pins npm 11.21.1).
- `npm ci`, then `npm run check`: build, package boundaries, schema artifacts, lint, format, unused code, and every test with coverage. A pull request is ready when `npm run check` passes.
- The full Highcharts schema cannot be distributed (license); `npm run build` generates it locally from the installed `highcharts`. Never commit anything under `packages/config/highcharts/src/generated/`.

| Script                            | What it does                                                                                |
| --------------------------------- | ------------------------------------------------------------------------------------------- |
| `npm run build`                   | `tsc -b` (project references), local Highcharts schema, playground and reference bundles    |
| `npm test`                        | Node test runner over every `tests/` directory of `packages`, `apps`, `scripts` and `tools` |
| `npm run test:coverage`           | Tests with c8 coverage thresholds (`.c8rc.json`)                                            |
| `npm run lint` / `fix-lint`       | ESLint (strict type-checked), zero warnings allowed                                         |
| `npm run format` / `fix-format`   | Prettier                                                                                    |
| `npm run knip`                    | Unused files, exports and dependencies                                                      |
| `npm run boundaries`              | Package dependency and import boundaries                                                    |
| `npm run schema:generate`         | Regenerate schema artifacts from the pinned upstream versions                               |
| `npm run schema:check`            | Fail if a committed schema artifact is stale                                                |
| `npm run api:check` / `api:write` | Compare / record the public API surface of every package                                    |
| `npm run check`                   | Everything above, then tests with coverage                                                  |

The schemas are generated by `tools/schema-generator` (with `@chartguard/schema-generator`) from the type declarations of the exact versions pinned in `packages/schema-generator/upstream-sources.json`, after checking the installed package against that pin and the lockfile; declarations are only type-checked, never executed, and every fact cites the line it was read from.

Git hooks (husky) only check, they never change files. Run `npm run fix-lint` and `npm run fix-format` yourself and review the diff.

## What a change needs

- **A test that fails without it.** A fix comes with the test that reproduces the defect; a feature with tests for valid, invalid and unknown input.
- **Unknown stays unknown.** The validator and the source analysis never turn something they cannot establish into a confident value or a confirmed error; they report it as partial or inconclusive.
- **No code execution.** Static analysis never runs the analysed code or a callback in it.
- **Independent packages.** A config package never imports another chart library or a chart runtime; `npm run boundaries` checks it.
- **Runtime evidence.** A claim about what a chart library accepts or rejects is backed by the runtime (`tools/conformance`), not by reading its types alone.
- **Public API.** If `npm test` reports an API surface change, decide whether it is breaking (major) or additive (minor), record it with `npm run api:write`, and add a changeset (`npm run changeset`) for each package that changes.
- Git hooks only check; they never rewrite files.

## Releases

Packages are versioned independently with Changesets. A change that should be released adds `npm run changeset`; the maintainer runs `npm run version-packages` (it also regenerates the schemas, which carry the generator's version), sets the `meta` versions of the ESLint plugin and the language server to their new manifest versions and the action pins users copy (README, the CI guide, `examples/github/chartguard.yml`) to `v<new CLI version>` (tests fail until they match), and commits. Publishing happens only in the `release` workflow, started by hand on `main` for a commit whose CI passed and approved by the maintainer: it deploys the site, publishes every package npm does not have yet through npm trusted publishing (with provenance), and the VS Code extension through Marketplace trusted publishing, then tags the commit (each package at its version, the action as `v<CLI version>`; a tag is never moved). Nothing is published from a machine.

## Issues and triage

New issues are labelled `needs-triage`. The maintainer then adds a kind (`bug`, `false-positive`, `false-negative`, `enhancement`), the area (`area:*`) and the chart library (`lib:*`), or asks for a reproduction (`needs-repro`).

- A **false positive** (an error the chart library does not have) needs the config, the library version, and what the library does with it.
- A **false negative** (a config the library rejects or ignores without a finding) needs the same, and is fixed only with runtime evidence.
- Behaviour of the chart library itself is labelled `upstream`.

Security issues follow [SECURITY.md](SECURITY.md), not the issue tracker.
